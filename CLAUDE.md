# CLAUDE.md

Personal portfolio for Daniel Lublinsky: a one-page site plus the CV PDF it links to.

## ⚠️ The one rule: two surfaces, always both

The same facts — jobs, titles, dates, bullets, skills, background — exist in **two** places
that do not share a source. Changing one and not the other ships a site and a CV that
contradict each other.

| Surface | Edit this | Then |
|---|---|---|
| Website | `mySite/index.html` | nothing — it's the deployed artifact |
| CV PDF | `cv/cv.json` | `node cv/build.mjs` to regenerate `mySite/daniel_lublinsky_cv.pdf` |

So: **update `mySite/index.html` AND `cv/cv.json`, then rebuild the PDF.** Any request
phrased as "update my experience / add this job / fix that date / add a skill" means all
three steps, even when the user only names one of them. State in your reply which surfaces
you touched.

The wording does not have to match verbatim — the site is chattier and carries more skills
than the one-page CV — but the *facts* must: company names, titles, date ranges, employment
type, locations. Never leave a title updated in one and stale in the other.

LinkedIn is the upstream source of truth for employment facts. The user usually supplies it
as a screenshot; transcribe it rather than inventing phrasing.

## Layout

```
mySite/            # exactly what gets deployed; nothing else is published
  index.html       # the whole site — inline CSS + JS, no build step, no dependencies
  daniel_lublinsky_cv.pdf    # GENERATED by cv/build.mjs — never hand-edit, it is overwritten
  stats.json       # GENERATED in CI by .github/scripts/build-stats.mjs — never hand-edit
  *.png / *.jpg
cv/
  cv.json          # CV content — the only file to edit for CV wording
  build.mjs        # renderer: cv.json -> cv.html -> PDF via headless Chromium
  cv.html          # GENERATED preview — never hand-edit, it is overwritten
  README.md        # flags, JSON shape, how to tailor a per-application variant
.github/
  workflows/deploy.yml      # force-pushes mySite/ to the gh-pages branch on push to main
  scripts/build-stats.mjs   # fetches GitHub stats -> mySite/stats.json (token lives in CI)
```

## Commands

```bash
node cv/build.mjs          # rebuild cv/cv.html and mySite/daniel_lublinsky_cv.pdf
node cv/build.mjs --watch  # rebuild on save while iterating
node cv/build.mjs --html   # HTML only, skip the PDF render
xdg-open mySite/index.html # the site has no build step — just open it
```

Verify a CV change actually rendered; do not assume:

```bash
pdfinfo mySite/daniel_lublinsky_cv.pdf | grep Pages        # must stay 1
pdftoppm -png -r 150 -f 1 -l 1 mySite/daniel_lublinsky_cv.pdf /tmp/cv && <read /tmp/cv-1.png>
```

**The CV must stay one page.** If content overflows, trim a bullet or drop `body` font-size
a notch in the `CSS` block of `build.mjs` — never let it spill to page 2 silently.

## Conventions

- **No build step, no dependencies, no CDN frameworks.** `index.html` is self-contained
  (devicon's stylesheet is the single external link); `build.mjs` is plain Node + Chromium.
  Do not introduce npm packages, bundlers, or a framework.
- Accent blue is `#2a5cff` in both surfaces. Keep them visually consistent — when the site's
  experience styling changes, consider whether the CV's should follow.
- Multi-title employers (currently Contiki) render as a company header with nested roles on a
  dotted timeline rail — hollow blue dots joined by a hairline connector, in both the site
  (`.exp-roles` / `.exp-role`) and the CV (`.roles` / `.role` in `build.mjs`). A new employer
  with several titles should follow the same shape in both.
- In `cv.json`, an experience entry is either flat (`bullets`) or nested (`roles`); both keys
  may coexist. See `cv/README.md` for the full shape.
- Commit only when asked. Deploy is automatic on push to `main` — a push publishes the site
  and whatever PDF is currently committed, so rebuild before pushing CV changes.
